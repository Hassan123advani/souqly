# Decisions Log

Format: **D-number — title** · context → decision → consequences.

**D-001 — Monorepo with npm workspaces** · Need shared types between client and server without publishing packages. → `shared/` is consumed as TypeScript source (`main: src/index.ts`). Vite compiles it for the client; `tsx` runs it in dev and `tsup` bundles it into the server build. → No build step for shared; one `npm install` at root.

**D-002 — Separate local git repo** · The user's home folder is already a git repo containing this project. → `souqly/` has its own `git init`. → Commits never touch the parent repo. Nothing is pushed.

**D-003 — Money in integer minor units, rates in basis points** · Floating point errors in prices, commission and voucher math. → All amounts stored as integers (paisa). Percentages as bps (1250 = 12.5%). → Display via `formatMoney()`.

**D-004 — JWT in httpOnly cookies with server-side sessions** · Need "log out all devices", sessions list and refresh-token theft detection. → Short access JWT (15 min) + opaque refresh token stored hashed in `Session` collection, rotated on each refresh; reuse of an old refresh token revokes all of the user's sessions. → Sessions page and admin "force logout" are simple DB updates.

**D-005 — Tenant isolation via StoreMember + storeContext middleware** · Multi-vendor data must never leak across stores. → Membership table `StoreMember {storeId, userId, role, customRoleId, permissions}`; seller routes get `req.store` only from membership. `x-store-id` header selects among the user's own stores. → One user may belong to several stores (owner of one, staff in another).

**D-006 — Dev fallbacks behind interfaces** · Must run with zero API keys. → `StorageService`, `EmailService`, `NotificationProvider`, `PaymentProvider`, `JobQueue`, each with a factory choosing the real implementation if env keys exist. In-memory MongoDB in development when `MONGODB_URI` is missing, auto-seeded on boot so the site is immediately usable. → Switching to real services is only an `.env` change.

**D-007 — Brand "Souq Dusk" design system** · Needs to feel premium, warm and trustworthy and distinct from Daraz (orange) and Amazon. → Deep teal primary + saffron accent + pomegranate for sales on a parchment background; lantern-arch motif in the logo. Plus Jakarta Sans / Readex Pro / Noto Nastaliq Urdu. → See CLAUDE.md "Design system".

**D-008 — Search without external engine** · No Algolia/Elastic keys. → MongoDB text index + a lightweight fuzzy layer (normalized trigram-ish regex on name/brand/tags, and Levenshtein-based "did you mean" against a vocabulary of product names, categories and stores). → Can swap to Atlas Search later behind `SearchService`.

**D-009 — Order split** · One checkout must create one order per store. → `Checkout` (parent, payment) → `Order` per store (sub-order, own status/timeline/shipping). Stock is decremented atomically with `findOneAndUpdate({stock: {$gte: qty}})` per variant; on any failure the already-decremented items are restored. → Works without replica-set transactions (memory server is standalone).

**D-010 — Images for demo data** · No copyrighted images allowed. → Seed generates original SVG placeholder product art (category-themed gradients + iconography + product name) stored via StorageService. → Fully offline, no licensing risk.

**D-011 — Refresh rotation: one Session doc per rotation** · Need reuse detection without false alarms from two tabs refreshing at once. → Refresh token = `<sessionId>.<random>`, only sha256 stored. Each refresh atomically revokes the old Session (`replacedBy` = new id) and creates a new one (keeps the original `createdAt`). Presenting a rotated token more than 15 s after rotation revokes ALL the user's sessions + audit `auth.refresh_token_reuse`; inside 15 s it returns 401 `SESSION_ROTATED` without clearing cookies. Rotated docs are TTL-deleted after 7 days (reuse detection window). An access token whose session was rotated returns `TOKEN_EXPIRED` so the client simply refreshes. → Sessions list only shows non-revoked docs.

**D-012 — Jobs are in-process only for now** · Redis/BullMQ are not installed. → `JobQueue` interface (`register`, `schedule`, `every`, `stop`) with an in-process setTimeout/setInterval implementation; no persisted Job collection. Scheduled jobs are lost on restart, so handlers must be idempotent and periodic sweeps must re-derive pending work from the DB. → A Redis implementation can be added behind the same interface when `REDIS_URL` is set.

**D-013 — Server test setup** · Fast, isolated, key-free tests. → vitest globalSetup starts ONE mongodb-memory-server; each test file uses its own random database. `NODE_ENV=test` never reads `server/.env` (so real SMTP/Twilio keys are never used by tests), rate limiters are skipped (`TEST_RATE_LIMIT=1` re-enables), bcrypt cost is 4 in tests (12 otherwise). Emails/SMS are captured in `consoleOutbox` / `notifyOutbox` from the console fallbacks.

**D-014 — Account schemas and API types live in @souqly/shared** · Client forms and server validation must agree. → Added `shared/src/schemas/account.ts` (profile, preferences, 2FA, mode, sessions, delete, verify-email) and `shared/src/types/api.ts` (`MeUser`, `Address`, `SessionInfo`, `PublicConfig`, `ApiError`).

**D-015 — Phone OTP details** · → Phones normalized to `+E.164`. If the account has 2FA, `/auth/otp/verify` also requires `totp` (401 `TOTP_REQUIRED`; the OTP stays valid for the retry). In production without Twilio, `/auth/otp/request` returns 503 `SMS_UNAVAILABLE` instead of pretending to send.

**D-016 — Change email is immediate + re-verify** · Per docs/api-auth.md. → Email is updated at once with `emailVerified=false` and a verification link goes to the new address (password required; audited with old/new address). No confirmation is sent to the old address yet (possible hardening later).

**D-017 — Local uploads are served inert** · Seed art is SVG (D-010) and users upload images. → `/uploads` responses carry `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` and `Cross-Origin-Resource-Policy: cross-origin`; avatar uploads are checked by magic bytes (jpg/png/webp, ≤ 2 MB).

**D-030 — Token-driven theming with inverted dark scales** · Need one class vocabulary that works in light and dark. → All colors are CSS variables holding "r g b" channels (`client/src/styles/tokens.css`) mapped in Tailwind with `<alpha-value>`. Under `.dark` the 50..950 scales are inverted, so tinted pairs like `bg-primary-50 text-primary-700` stay readable; solid brand fills use semantic tokens (`bg-primary text-primary-fg`, dark mode = light teal with dark text for AA contrast). → Components rarely need `dark:` variants. A subtree can be forced dark by adding the `dark` class (used for the auth panel and hero banners).

**D-031 — Logo: souq arch + saffron "S" + lantern dot** · Brand mark must be original and readable at 16px. → A pointed souq-doorway arch in deep teal carrying a saffron "S" ribbon with a lantern dot at the apex (it also reads as a price tag). Lockup = mark + "Souqly" (Plus Jakarta 800, "ly" in teal) + "سوقلي" (Readex Pro, saffron). The React `Logo` uses token colors (`--logo-arch`); PNG icons, maskable icon and OG image are generated from SVG by `client/scripts/generate-brand-assets.mjs` (headless Chromium).

**D-032 — Fonts per language** · Nastaliq is tall and its Latin glyphs are serif. → `html[lang=ur]` uses the stack Plus Jakarta Sans → Noto Nastaliq Urdu with line-height ~2 (Latin names, emails and numbers keep the brand face); `html[lang=ar]` uses Readex Pro. Codes, prices and OTP boxes are forced LTR (`dir="ltr"`, `.latin`).

**D-033 — Theme/language before first paint** · Avoid a flash of the wrong theme or direction. → The zustand UI store persists as `souqly-ui`; an inline script in `index.html` reads it and sets `<html class="dark" lang dir>` before React loads. i18next detects language from the html tag. When a user signs in, their saved preferences are adopted once; switcher changes are saved to `PATCH /account/preferences` when signed in.

**D-034 — Shared Zod schemas, translated client-side** · Schemas in `@souqly/shared` carry English messages. → The client installs a global Zod error map (built-in issues translated) and maps the schemas' custom English messages to `validation.*` keys (`client/src/lib/validation.ts`). → No duplicated schemas; all form errors are localized.

**D-035 — Unbuilt areas are hidden, not broken** · Seller/Admin navs and marketplace tabs reference later phases. → Dashboard nav items carry `ready: boolean` and only ready items render. Marketplace links (categories, search, cart, wishlist, chat) go to a real "coming in this release" page; the seller-onboarding CTA is behind `WIZARD_READY = false` and an honest notice. → No dead buttons; flipping a flag reveals a feature.

**D-036 — Guards and auth UX** · `RequireAuth` / `RequirePlatformStaff` / `RequireSellerMode` wait for `/auth/me` (no retries) and show a retryable error if the API is unreachable; `RequireGuest` never blocks rendering (login works even while the session check fails). `next` redirects accept only same-origin relative paths. Refresh-on-`TOKEN_EXPIRED` is single-flight in the axios interceptor.

**D-037 — Visual QA with a fixture-backed API mock** · The UI must be reviewable while the server is down or busy. → `e2e/screenshots.mjs` (BASE_URL env or `--base`) takes desktop 1440×900 and mobile 390×844 shots in light/dark per language, records `pageerror`/`console.error`, and `--mock` serves fixture `/api/v1` responses (signed-in user, addresses, sessions; `--admin` for a staff user).

**D-018 — Catalog visibility via an approved-store index** · Public products must belong to `approved` stores, but Product has no store status. → `getPublicStoreIndex()` (30 s in-process cache) lists approved stores (slug, name, isMall, city, holiday). Every public query adds `status: 'published'`, `deletedAt` absent and `storeId ∈ approved`. Holiday-mode stores stay visible; their cards carry `unavailable: true` and the detail page has `holidayMessage`. Store-level filters (`store`, `mall`, `city`) narrow that id list. → No denormalized store flags on products; caches are disabled under NODE_ENV=test.

**D-019 — Listing engine = one aggregation, cursor per sort** · Need 7 sorts with cursor pagination, including relevance. → `/products` runs `$match → ($addFields _rel) → cursor $match → $sort {field, _id} → $limit+1`. Relevance = `textScore + 0.15·ln(sold+1) + 0.1·rating` (popularity only when there is no text match). The existing `{v, id}` cursor encodes the sort value (works for the computed `_rel` too). `total` only on the first page; `facets=1` adds a `$facet` (brands, price range, rating buckets, colours, sizes from `variants.options`). `relevance` without `q` behaves like a popularity sort.

**D-020 — Search cascade details (D-008)** · → `$text` first (english stemming); if no hit, AND of per-token fuzzy regexes on `searchText` (`s.?h.?r.?t`); if still none, Levenshtein (≤1 for tokens ≤4 chars, else ≤2) against a vocabulary (category/brand/store names + published title tokens and tags, weighted, rebuilt lazily every 10 min) and results for the corrected query with `meta.didYouMean`. `/search/suggest` also returns `didYouMean` when the exact text search missed but fuzzy matched. Searches are logged to `SearchLog` (first page only); `DELETE /search/history` detaches the user id rather than deleting rows, so trending counts stay.

**D-021 — Product card/derived fields** · → `recomputeDerived()` (pre-save, and called explicitly before `insertMany`) sets `priceMin/priceMax/compareAtMax/discountPct/totalStock` plus an extra `compareAtMin` (compare-at of the cheapest variant) so a card can show "was/now" without loading variants. `totalStock` counts active variants, stock − reserved. `stockLeft` is sent only when `< 10`.

**D-022 — Seller products** · → `/seller/products*` behind `requireAuth + storeContext + requirePermission(store.products.view|manage)`. Every lookup is `{_id, storeId: req.store._id}` (foreign ids → 404). Schemas are `.strict()`, so `storeId`/`status`/counters in the body are rejected (400). Descriptions/size guides go through `sanitizeRichText`; other strings through `stripHtml`. Media URLs must be `/uploads/...` or `https://res.cloudinary.com/...`. Editing keeps variant ids/`reserved` when `id` is sent. DELETE is a soft delete (`deletedAt` + `archived`). Publish → `published` for approved Mall stores or when the `autoApproveProducts` setting is true, otherwise `pending_review`.

**D-023 — Seller uploads** · → `POST /seller/uploads` (multipart `file`, multer limit 30 MB) sniffs magic bytes: jpg/png/webp/avif images ≤ 5 MB, mp4/webm videos ≤ 30 MB; stored under `stores/<storeId>/images|videos`. Uploads are audited.

**D-024 — Seed art at fixed keys** · Re-seeding the in-memory dev DB on every boot would pile up files. → `UploadOptions.fixedKey` (seed only) writes art to deterministic paths under `seed/` (products, stores, home, campaigns), so a re-seed overwrites identical files. `seed:clear` wipes the `seed/` folder (local) or deletes the seed keys (Cloudinary). Seed content is deterministic (mulberry32 PRNG seeded per store/product), so `runSeed({reset})` reproduces the same slugs, prices and counts. Demo password is bcrypt-hashed once per run and reused for every demo user.

**D-025 — Public store DTO is an allow-list** · → `toStorePublic` builds the response from named fields only; `business`/`payout` are also `select: false`. Never exposed: `ownerId`, contact email/phone (only `contact.whatsapp`), `business`, `payout`, `healthScore`, `plan`. The `store` query param on `/stores/:slug/products` is ignored (scope is forced to that store).

**D-040 — Curated category icon registry** · Category `icon` is a lucide name chosen by admins; importing all of lucide adds ~1,500 icons to the bundle. → `client/src/components/catalog/CategoryIcon.tsx` maps ~60 named icons (plus aliases such as `Blender`→`Microwave`, `Home`→`House`) and falls back to `Tag` for unknown names. → To use a new icon, add it to the map.

**D-041 — Seller HTML is rendered as server-sanitized** · Descriptions, size guides and store policies are HTML. The server sanitizes them on write (allow-listed tags/attributes), and the client has no DOMPurify. → The client renders them with `dangerouslySetInnerHTML` inside a `.prose-souq` container. Free-text store section config (`text`/`banner`) is rendered as plain text, and CMS links go through `safeInternalLink` (same-origin relative paths only). → If any HTML ever reaches the client without server sanitizing, add DOMPurify first.

**D-042 — Store theming and layout templates** · Stores pick a `themeColor` and one of 4 `layoutTemplate`s. → The store page sets scoped CSS vars (`--store`, `--store-deep`, `--store-fg`, `--store-accent`). `--store-fg` is white or ink, whichever contrasts better with the brand fill. `--store-accent` is the brand color darkened or lightened until it reaches ≥ 4.5:1 on the light or dark surface. Templates: **classic** (banner + overlapping profile card, product rails), **bold** (full brand-gradient hero, uppercase brand-colored section bars, dense 6-up grids), **boutique** (centered profile, letter-spaced headings, airy 4-up grids), **minimal** (no banner, plain headings, compact 6-up grids). Grids are trimmed to complete rows.

**D-043 — Listing filters live in the URL; client-side delivery estimate** · Filtered listings must be shareable and back-button safe. → All filters, sort and the store search are query params. URL prices are in major units (`priceMin=1500`) and converted to minor units for the API; attribute filters use `a.<key>=v1,v2` → `attrs[key]`. Grid/list view is a persisted preference (`souqly-listing`). The delivery estimate is computed on the client: processingDays + 1–2 days within the store's city, or 3–5 days for other cities. The chosen city is remembered in `souqly-delivery-city`.

**D-044 — Guest cart, recently viewed and recent searches in localStorage** · The cart arrives in Phase 6, but Add to cart must work now. → The zustand `useCart` store is persisted as `souqly-cart` with lines `{productId, variantId, qty, snapshot}`; the header and bottom-nav badges read `count`. Buy now adds the line and opens `/cart`. "Add all" in Frequently bought together adds each companion's first in-stock variant, fetching its detail first. Recently viewed is saved to localStorage for everyone; signed-in users read the server list and fall back to the local one. Recent searches are kept locally and merged with the server history when signed in.

**D-045 — CMS banners carry their own artwork text** · Seeded hero, campaign and store banners have their headlines baked in. → The hero carousel shows the image as-is, with the CTA chip overlaid and the title kept as alt text. Campaign pages put their details in a strip below the banner. Store banners always use the full 4:1 image (never cropped). Translated headlines for banners need text-free art or per-language images; this is a CMS decision for Phase 9.

**D-046 — Unbuilt marketplace actions stay hidden (follows D-035)** · → `WISHLIST_READY`, `REVIEWS_READY` (ProductPage), `FOLLOW_READY` and `CHAT_READY` (SellerCard, also used by StoreHeader) are all `false`, so those buttons and sections do not render until their APIs exist.

**D-038 — Google sign-in honours 2FA and never inherits unverified accounts** · Security review H1/H2. → With 2FA on, the Google callback creates no session: it issues a single-use `google_2fa` Token (sha256 stored, 5 min, burned after 5 wrong codes) and redirects to `CLIENT_URL/login?google2fa=<ticket>`; the client finishes with `POST /auth/google/2fa {ticket, totp}`. Linking by email requires `emailVerified`; an unverified account is reset first (password, 2FA, phone, sessions, tokens, user OTPs; audit `auth.google_link_reset`).

**D-039 — Login lockout by atomic attempt reservation; generic 401 while locked** · Review M2/L2. → Each password/TOTP attempt first `$inc`s `failedLoginCount` only while `< 5` and unlocked; failures lock for 15 min when the budget is spent, success resets only if still unlocked, `TOTP_REQUIRED` gives the attempt back. Locked, unknown and wrong-password logins all return the same 401 `INVALID_CREDENTIALS` (423 `ACCOUNT_LOCKED` removed). Forgot-password is fire-and-forget.

**D-040 — Re-authentication + recovery codes + TOTP replay guard** · Review M3/L3/L10. → `requireReauth`: `password` if the account has one, else `otpCode` from `POST /account/reauth/otp` (OTP purpose `reauth`, sent to the verified phone); Google-only accounts (no password, no phone) have nothing to ask for and pass (recorded as `reauth: 'none'` in the audit). Required for 2FA setup/enable/disable, phone change and account deletion; `2fa/setup` checks the OTP without consuming it so one code covers the setup → enable wizard. Enable returns 8 recovery codes `XXXXX-XXXXX` (sha256 stored, single use) accepted wherever a TOTP is. `twoFactor.lastStep` makes every TOTP single-use. Notice emails on 2FA on/off, recovery-code use, email change (to the old address) and phone change.

**D-041 — Phones are verified before they are set** · Review M4. → `phone` only ever holds an OTP-proven number; `PATCH /account/profile {phone}` stores `pendingPhone` and texts an OTP (purpose `phone_change`), `POST /account/phone/verify` promotes it. OTP login matches `{phone, phoneVerified: true}` only; whoever proves a number takes it from unverified legacy holders. The unique index is now `phone_verified_unique` (partial on `phoneVerified: true`); `index.ts` drops the legacy `phone_1` index on boot. `Otp` docs carry `purpose` (`login|reauth|phone_change`) and `userId`; hashes include the purpose.

**D-042 — Production env hardening** · Review H3/M1/M5/M6/L8. → Production requires `DATA_ENCRYPTION_KEY` (≥ 32) and a strong `ADMIN_PASSWORD` (≥ 12, not `souqly123`/deny-list); the seed refuses a weak admin password and skips demo data unless `--demo`. `TRUST_PROXY` (default false; hop count / `loopback` / IP list; `true` refused in production) replaces the hard-coded `trust proxy 1`. OTP `devCode` needs `DEV_OTP_ECHO=1` (off by default, set in `.env.example` for local dev and in vitest config; refused in production and with a non-local `MONGODB_URI`). The console email fallback redacts bodies in production. `parseEnv()` is exported for tests.

**D-043 — JSON-only API mutations (CSRF)** · Review L9. → No urlencoded parser. POST/PUT/PATCH/DELETE need `Content-Type: application/json` (multipart only on `/account/avatar` and `/seller/uploads`, see `MULTIPART_PATHS`) or, when bodyless, an `X-Requested-With` header (forces a CORS preflight; the axios client always sends it) → otherwise 415 `UNSUPPORTED_MEDIA_TYPE`. Tests use `newAgent()`/`xhr()` which set the header.

**D-044 — Security-sensitive endpoints are closed to impersonators; misc hardening** · Review L1/L4/L5/L6/L7/L11. → `forbidWhileImpersonating` on change-password/email, phone change/verify, reauth OTP, 2FA, revoke-all and delete account. Change-email revokes other sessions and kills reset links (reset also requires the link's email to match). `storeContext` returns 403 `STORE_SUSPENDED` for suspended/rejected stores (pending stays usable for setup). Sockets: foreign `Origin` refused, sockets join `session:<sid>` and are disconnected on revoke. OTP limits: request 5/15 min per normalized phone + 20 per IP; verify 10 per phone + 30 per IP. The Google callback query string is redacted in request logs.

**D-047 — Seller KYC / bank secrets: ciphertext + last4 only** · Phase 5. → `business.cnicOrRegNo`, `payout.accountNumber` and `payout.iban` are stored as AES-256-GCM `*Enc` (lib/crypto `encrypt`, `DATA_KEY`) plus `*Last4`; DTOs mask from `*Last4` (`****1234`) and never decrypt. `business`/`payout`/`pickupAddress` stay `select: false`. Onboarding / store media must be a Souqly upload under a folder the caller owns (`tmp/{userId}/` via `POST /uploads/temp`, or `stores/{storeId}/`) — `INVALID_MEDIA` otherwise. Temp uploads: image or PDF (magic bytes), ≤ 5 MB.

**D-048 — Seller routes outside the regular storeContext** · Phase 5. → `sellerPreStoreRouter` is mounted at `/seller` before `sellerRouter`: `POST /onboarding`, `GET /invitations`, `POST /invitations/:id/accept|decline` (requireAuth only) and `GET /store`, `PATCH /store/payout|business` (with `storeContextAllowRejected`, so a REJECTED store can read its reason and resubmit; resubmitting business/payout moves it back to `pending`). Suspended stores stay locked out everywhere (D-044, security). `PATCH /store/business` is OWNER-only (`requireStoreOwner`).

**D-049 — Custom store roles** · Phase 5. → `STORE_ROLES` gains `CUSTOM` (permissions `[]` in `STORE_ROLE_PERMISSIONS`); a CUSTOM member's permissions come from `CustomRole {storeId, name, permissions}` resolved by `storeContext` on every request (role edits apply immediately; a missing role grants nothing; results are always filtered to `store.*`). Anti-escalation: creating/editing a role and assigning any role (built-in or custom) require the actor to hold every permission granted. OWNER memberships cannot be changed or removed; members cannot change their own access; a role still assigned cannot be deleted.

**D-050 — Staff invitations** · Phase 5. → Inviting an existing user creates `StoreMember {status: 'invited', invitedBy}` (storeContext ignores it) + a console email; the invitee accepts/declines via `/seller/invitations/:id/*` (matched on their own userId). Unknown email → only a signup email is sent and no record is kept; the owner re-invites after signup (no pending-email table yet).

**D-051 — Inventory ledger** · Phase 5. → `adjustStock()` in `modules/inventory/inventory.service.ts` is the reusable entry point (always storeId-scoped): guarded `$inc` (`stock >= -delta`, and per warehouse `warehouseStock.qty >= -delta` when `warehouseId` is given; first stock into a warehouse pushes a qty-0 slot), then a pipeline update recomputes `totalStock` (sum of `stock - reserved` over active variants), then `recordMovement()` writes `StockMovement {…, ref, actorId, balanceAfter}`. `recordMovement()` alone is exported for callers that already changed stock (checkout). 404 for foreign product/variant/warehouse, 409 `INSUFFICIENT_STOCK`. Manual adjustments are not limited by `reserved` (only by 0). Warehouses: first one becomes default, one default per store (partial unique index), cannot delete a warehouse holding stock.

**D-052 — Dashboard data sources** · Phase 5. → Order metrics read the Phase-6 `Order` model lazily via `mongoose.model('Order')` only if registered (fields used: `storeId, status, total, items[].qty, number, createdAt`; sales exclude `pending_payment|cancelled|returned|refunded`); zeros otherwise. Visitors come from `StoreVisit {storeId, date (UTC YYYY-MM-DD), views, visitors}` incremented fire-and-forget on public store page and (view-deduplicated) product page views; unique visitors are deduped per process per day. Deltas are % vs the previous equal window (`null` when previous = 0 and current > 0). Health score = rating 0.3 + response rate 0.2 + (1 - cancellation rate) 0.25 + listing quality (≥ 3 images and ≥ 80-char description) 0.25. `unansweredQuestions`/`unreadChats` are 0 until Phase 8. Store-scoped activity log = `AuditLog.storeId` (auto-filled from `req.store` by `audit()`).

**D-053 — Store settings document** · Phase 5. → `StoreSettings {storeId unique, shipping, notifications, chat}`; missing sections return defaults (shipping: one `Nationwide` zone `cities: 'all'`, Rs 200, 2-5 days, processing 1 day; low-stock threshold 5). `getShippingSettings(storeId)` is exported from `modules/seller/storeSettings.service.ts` for Phase 6. Shipping is replaced as a whole on PUT; notifications/chat are merged.

**D-054 — Facets exclude their own filter; card default variant** · Phase 4 gaps. → `computeFacets` matches the non-facet filters once, then each facet re-applies every facetable filter except its own (brand, price, rating, color, size). `ProductCard.defaultVariantId` = cheapest active in-stock variant (fallback cheapest active). Store summary on product detail carries `city`. `DELETE /search/history/:q` detaches one normalized query from the user's history.

**D-055 — Phase 6 pricing order & money rules** · `server/src/modules/orders/pricing.ts` (pure, unit-tested). → Unit price = min(base, active flash price, best wholesale tier reached by qty). Store voucher on that store's eligible lines; platform voucher on all eligible lines after store discounts, prorated across stores by eligible share (floored; rounding remainder to the largest share, capped per share). Shipping per store: zone rate for the buyer city; free when store subtotal ≥ `freeAbove` or every line is `freeShipping`; store `free_shipping` voucher waives that store; platform `free_shipping` voucher waives shipping across stores up to `maxDiscount`. `discountTotal` = voucher discounts incl. voucher-waived shipping (threshold-free shipping is not a "discount"). Coins = 0 (Phase 8 hook). Commission base = items − store discount (platform-funded discounts do not reduce it); `sellerNet = base + shipping − commission`.

**D-056 — Shipping defaults & commission resolution** · Contract Phase 6. → Stores with no saved shipping settings (Phase 5 `getShippingSettings` returns its `DEFAULT_SHIPPING` object) use city-relative defaults: Rs. 150 same city as the store, Rs. 250 elsewhere, free above Rs. 3,000 (`cart/shipping.ts`). `CommissionRule` resolution: store > deepest matching category (highest rate when lines span categories) > global > hard default 1000 bps. Rate + amount are snapshotted on the order.

**D-057 — Checkout atomicity without transactions** · mongodb-memory-server is not a replica set. → Order: claim the idempotency key (`Checkout{userId, idempotencyKey}` unique, `state: processing`) → take voucher uses (`usedCount < usageLimit` guarded `$inc`) → reserve stock per variant (`variants.$elemMatch {stock ≥ qty}` + `$inc` stock/totalStock/soldCount, stable order) → insert orders. Any failure undoes the earlier steps (compensating `$inc`) and DELETES the checkout so the key is reusable; concurrent retries with the same key wait for the first attempt and get its result (200; first = 201). Before reserving, the server re-prices the cart; any issue on selected lines (unavailable/out_of_stock/qty_reduced/price_changed) → 409 `CART_CHANGED` with `details.issues`; a lost stock race → 409 `STOCK_CHANGED`. Sales are taken from the variant's unassigned stock (warehouse allocation of online sales is a later concern). Stock movements `sale` / `cancel` go through Phase 5 `recordMovement`.

**D-058 — Order numbers, payment, OTP, PDFs** · → Checkout `SQ-YYMMDD-XXXXX` (UTC date + 5 chars of the unambiguous `randomCode` alphabet, unique index); sub-orders `-A`, `-B` … (`-AA` after Z); invoice `INV-YYMMDD-XXXXX-A`. Only COD is placeable; other methods → 400 `PAYMENT_NOT_CONFIGURED` (gateways not built even with keys). On `shipped` a 4-digit delivery OTP is generated: `deliveryOtpHash = sha256(orderId:otp)` (for rider verification in Phase 7) + AES-GCM `deliveryOtpEnc` (both `select: false`) so ONLY the buyer's order detail can show it while shipped/out_for_delivery/failed_delivery; the plain code is SMSed to the shipping phone. Seller DTOs never include it. Invoice (A4) and label (4x6 in, QR of the order number) are rendered with PDFKit core fonts (non-Latin-1 characters become `?`). Buyer order endpoints return 404 for other buyers' orders (no enumeration); invoice is also readable by active members of the selling store and staff with `admin.orders.view`.

**D-059 — Seller order actions** · → Sellers can move orders only to `confirmed|packed|shipped|cancelled` (rider/returns statuses come in later phases); bulk status only `confirmed|packed`. Cancel needs a reason (buyer or seller) and restores stock exactly once (`stockRestored` claim). Buyers may cancel while `pending_payment|placed|confirmed`. Transitions are compare-and-set on the current status (409 `ORDER_CHANGED` on a lost race). `assign-rider` accepts an active StoreMember of the same store whose effective permissions include `store.delivery.perform`. Authenticated sockets join `store:{id}` for each active membership; `order:new` / `order:updated` are emitted there (buyer gets `order:updated` on `user:{id}`).

**D-060 — Buyer cart sync & checkout client** · → `useCart` (zustand) stays the single entry point: `mode: 'guest' | 'server'`; guests keep lines in localStorage, signed-in users use the server cart (TanStack Query `['cart']`). `<CartSync />` (mounted in App) merges the guest lines once per login via `POST /cart/merge`, removes only the merged lines locally, then registers a server adder so `useCart.add` (ProductPage / BoughtTogether, unchanged) posts to `/cart/items`; the badge `count` follows the active cart. Per-store "select all" patches lines one by one (no bulk endpoint). Checkout keeps one `idempotencyKey` (crypto.randomUUID) per attempt: reused if the request got no response (network retry can't double-order), regenerated after any server answer. 409 `STOCK_CHANGED|CART_CHANGED` refresh cart + preview and explain inline. Contact-seller / request-return buttons are gated by flags `chat` / `returns` (hidden until Phase 8 / 7). Feature strings live in `i18n/locales/shop/*.json` (keys `cart`, `checkout`, `orders`). Vite proxy target is overridable with `VITE_API_PROXY`.

**D-061 — Notifications & push (Phase 7)** · → `notify({userId,type,title,body,link?,data?,channels?})` in `modules/notifications/notification.service.ts` is the single entry point (default channels `inapp`+`push`; email/SMS/push respect `User.preferences.notifications`; never throws; only relative `link`s kept; never put OTPs/tokens in it). In-app rows TTL 180 days. Order lifecycle → buyer in-app/push (`order.<status>`); emails/SMS for status changes stay in `order.service` to avoid duplicates. New order / cancel / return → owner + members whose effective permissions include `store.orders.view`. Web push via `web-push` only when VAPID keys exist; subscriptions are stored regardless (endpoint unique, moves between accounts).

**D-062 — Riders, OTP, live location (Phase 7)** · → A rider = active StoreMember with effective `store.delivery.perform` (so store OWNERs qualify for their own store); access to an order additionally requires `order.riderId == me` (otherwise 404). One `DeliverySession` per order holds attempts, OTP counter and lock (5 wrong → 423 `OTP_LOCKED` 15 min; counter survives rider swaps), COD collected, earning (flat `DeliverySettings.riderFee`, default 12000 paisa) and `lastLocation`. Deliver is allowed from `shipped|out_for_delivery`; COD collected ≤ due (full amount marks payment `paid`); one `collected` cash entry per order (unique partial index); seller settlement ≤ outstanding. Locations: assigned rider + `out_for_delivery` only, ≥3 s apart per rider/order (in-memory limiter), stored in `RiderLocation` (TTL 7 days). Socket `order-track:join` only for buyer / store member / `admin.orders.view` while out for delivery (404 for others, 409 `TRACKING_INACTIVE`); delivered/failed emit `tracking:ended` and empty the room. Tracking HTTP returns rider (masked phone) / location / ETA (haversine ÷ 25 km/h) only during out_for_delivery. Order address snapshots now copy the address pin (`shippingAddress.location`). Uploads (delivery proof, return photos) return an AES-GCM sealed `ref` (`{key,url,userId,purpose}`) that clients send back, so client URLs are never trusted.

**D-063 — Returns & refunds (Phase 7)** · → One `ReturnRequest` per order (unique). Only `delivered` orders, within every returned product's `returnPolicy.days` (default 7, 0 = not returnable) counted from the last `delivered` timeline entry. Flow: requested → approved|rejected; approved → received (restock once via `adjustStock` reason `return`) → refunded; requested|rejected → escalated (creates `Dispute`, for admin in Phase 9). Order follows delivered → return_requested → (reject: delivered) → returned → refunded. Refund amount = min(Σ price×qty, order.total), always to the wallet via Phase-8 `wallet.credit` with ref `refund:<returnId>` (idempotent) before the compare-and-set to `refunded`, so concurrent/duplicate refunds credit once.

**D-064 — Reviews, Q&A & moderation (Phase 8)** · → Only the buyer of an order in `delivered|return_requested|returned|refunded` may review an item of it; one review per order item (partial-unique `orderId+productId+variantId`; unverified seed reviews have `orderId: null`). Text is plain (HTML stripped); a small EN/Roman-Urdu list (`reviews/badWords.ts`) is masked (`s***`) and the review/question goes to `pending` (moderation) instead of being rejected. 5 reports → `pending`. Product/Store `ratingAvg/ratingCount` are recomputed from published reviews on every change. Fraud signals (`FraudSignal`, admin queue): account < 24 h, ≥ 5 reviews/hour, same IP as a store-owner session (skipped for loopback/private IPs, which say nothing in dev/proxy setups; owner-IP also holds the review as `pending`). Review/chat media are uploaded first via `POST /social/uploads` and recorded in `SocialUpload`; reviews/messages may only reference the sender's own keys of the right kind. Seller review/Q&A routes are mounted per-route (`requireAuth, storeContext, perm`) under `/seller` so other `/seller/*` routes are unaffected; review reply = `store.chat.manage` or `store.orders.manage`.

**D-065 — Chat** · → One `Conversation` per buyer+store (unique). Access = the buyer, or an active member of a non-suspended store whose effective permissions include `store.chat.manage`; the same check guards socket `chat:join` into `conv:{id}` (typing requires a prior authorised join). Message text goes only to the conv room; `user:`/`store:` rooms only get `chat:conversation {id, unread}` (store rooms include members without chat permission). Product/order cards are snapshots; order cards must belong to this buyer AND store (whoever sends them). Auto-reply from store chat settings: once per conversation per 12 h, only when no socket is in `store:{id}`. Response stats: a buyer message opens a "thread" (`pendingSince`), the first human store reply answers it; `Store.responseRate` = answered/asked, `responseTimeHours` = mean first-response time over all conversations.

**D-066 — Wallet, coins, referrals, gift cards** · → Wallet and coin ledgers are ledger-first and idempotent: insert a `pending` row with a unique `ref` (duplicate → no-op), then atomic `$inc` on `User.walletBalance` / `User.coins` (debits conditional on balance; failure deletes the claim), then mark `done`. Coins: 1 per Rs. 100 of `order.total` on delivery (ref `order:<id>`, flag `loyaltyCoins`); check-in once per Asia/Karachi day (unique `userId+day`), 10 coins, +50 on every 7th consecutive day (flag `dailyCheckIn`). Redemption: 100 coins = Rs. 10, max 20% of the total after vouchers+shipping, prorated across store orders as `discounts.coins` (platform-funded: `sellerNet` unchanged); coins are spent at checkout with ref `checkout:<id>` after stock is reserved and refunded if order creation fails. Coins are NOT refunded on later cancel/return yet (Phase 9). Wallet is not a payment method yet. Referral: on the referee's first delivered order, unique `ReferralReward.refereeId` → referrer Rs. 200 wallet + referee 500 coins (flag `referrals`). Gift cards: single redemption claimed atomically (`redeemedBy: null` → user) then credited to the wallet (ref `giftcard:<id>`); redeem is rate-limited 10/h/user (flag `giftCards`).

**D-067 — Follows, wishlists, alerts, reports** · → `Follow` (unique user+store) keeps `Store.followerCount` with $inc; `isFollowing()` backs follower-only vouchers. Wishlists: up to 20 named lists × 500 items, one default "My wishlist" (partial-unique); `Product.wishlistCount` = number of users with the product in any list. Alerts (`price_drop` re-arms at the new price after notifying; `back_in_stock` fires once) are checked after seller product updates and by a 10-minute `alerts.sweep` job. `Report` is unique per reporter+target; message reports require being a participant of the conversation.

**D-068 — Seller Center frontend (Phase 5/6)** · → Every Seller Center request sends `x-store-id` = the *resolved* active store (persisted choice in zustand `souqly-seller-store` if still a membership, else the first store), and all seller query keys start with `['seller', storeId]`, so switching stores never mixes caches. Rich description = contentEditable + execCommand emitting HTML (server sanitizes). Live orders: `lib/socket.ts` ref-counted socket.io client (`withCredentials`), `order:new` → toast + WebAudio chime (mute persisted in `souqly-seller-prefs`, alongside tour/checklist dismissal) and orders/dashboard invalidation. `DashNavItem` gained optional `badge` (low-stock count) and `tourId` (`data-tour` anchor for the first-visit tour). Vite proxy target is overridable with `VITE_API_PROXY`.

**D-069 — Phase 6–8 follow-ups** · → Each store order stores `coinsUsed` (whole coins, split with the coin-discount weights). Cancel (buyer/seller/admin, incl. forced) and return refunds (seller refund + admin dispute refund) give coins back via `refundOrderCoins` with ledger ref `coins-refund:<orderId>`: one refund per order, partial returns get `floor(coinsUsed × returnedItemsValue / subtotal)`. Google sign-in accepts `?next=` (only `safeNextPath`: starts with `/`, not `//` or `/\`, no control chars/backslash, ≤ 300), stored in a callback-path cookie and on the 2FA ticket; redirects carry `&next=`, `POST /auth/google/2fa` returns `next`. Seller products: `meta.counts` per status + `all`; bulk publish/archive reports per-id failures; archiving a live product drops `productCount` and clears `publishedAt`. `GET /seller/orders/riders` (orders.view) for the rider picker; `GET /catalog/categories/:slug/attributes` returns every effective attribute. Tracking returns the rider's real phone only to the order's buyer while `out_for_delivery`; others get it masked. `GET /seller/returns` adds `meta.counts`.

**D-070 — Super Admin API (Phase 9)** · → Contract in `docs/api-admin.md`. Every admin route uses `can(perm)` = requireAuth + "not impersonating" + requirePermission; every mutation and CSV export is audited. GMV = Σ total of orders not `pending_payment|cancelled`; revenue = commission of orders not also `returned|refunded` (Asia/Karachi day buckets). Impersonation: ADMIN_USERS_IMPERSONATE, reason required, never staff/admins or inactive users; the admin's session is revoked and replaced by a 1-hour session flagged `impersonatorId`; `POST /admin/impersonation/stop` revokes it and starts a fresh admin session (only if the impersonator is still active staff). Product hide = `rejected` + note (seller resubmits through review). Admin order status override: valid transitions run normal side effects, others are forced (`forced: true` in audit; stock + coins restored on forced cancel). Admin refunds are capped by `adminRefunded ≤ total` (conditional `$expr` update) and credited with ref `admin-refund:<orderId>:<runningTotal>`. Category move updates the node immediately and recomputes descendants' `ancestors` + products' `categoryPath` in the `catalog.recomputeCategoryPaths` job (idempotent). Settings keys: `site` (incl. maintenance), `featureFlags` (known keys only, merged), `paymentMethods` (offered = enabled AND keys present; checkout rejects disabled methods with `PAYMENT_DISABLED`), `shippingZones`, `tax`. Maintenance: non-staff (and impersonated sessions) get 503 `MAINTENANCE` except `/auth`, `/config/public`, `/health`, `/pages`. CSV: streamed from cursors with a BOM; cells starting `= + - @ \t \r` get a `'` prefix. `Payout` model (requested → approved → paid, requested|approved → rejected; method snapshot masked). Support tickets: buyers see staff replies as "Souqly Support"; max 10 open tickets per user. System health exposes integration booleans only, job stats and the last 50 error-handler events (in-memory ring). CMS pages are seeded in every environment (`$setOnInsert`, never overwriting edits).

## Deploying to Vercel

**D-077 — One Vercel project: static client + Express API as a serverless function** · Owner decision: host everything on Vercel (no separate always-on server). → `vercel.json` at the root installs the npm workspaces (`MONGOMS_DISABLE_POSTINSTALL=1 npm ci --include=dev`), builds the client (`client/dist` = output) and the server bundle (`npm run build:vercel -w server`: tsup ESM/node20 of `src/vercel.ts` → `server/dist-vercel`, `@souqly/shared` bundled through `server/tsup.config.ts` since the tsup CLI has no noExternal flag — this also fixed the broken `--no-external` flag of `npm run build`). `api/index.mjs` re-exports the bundle's default handler, which lazily connects Mongo (small pool: max 5) and runs the same `app` as local dev; init failures answer JSON 503 and retry on the next request. Rewrites send `/api/*`, `/uploads/*`, `/sitemap.xml`, `/robots.txt` to the function and other non-file paths to `/index.html` (`/assets/*` excluded so stale chunks 404). `includeFiles` ships PDFKit's AFM/ICC data and `server/package.json`. `env.SERVERLESS` (default `!!VERCEL`; the Vercel entry forces it) means: `/config/public` → `integrations.realtime: false` (new field in shared `PublicConfig`; clients poll), no Socket.io (every emit already no-ops without `getIO()`), no in-process timers, `MONGODB_URI` mandatory, and storage without Cloudinary is `UnavailableStorage` (uploads → 503 `STORAGE_NOT_CONFIGURED`; the function disk is read-only). Category moves recompute paths inline instead of via a timer (`recompute: 'done'`). Periodic work is a registry (`services/jobs/sweeps.ts`: `alerts.sweep`, `storeHealth.recompute`, `catalog.recomputeCategoryPaths`; other modules add entries there) exposed at `GET|POST /api/v1/internal/cron/:name|all`, authorised by `Authorization: Bearer ${CRON_SECRET}` (sha256 + `timingSafeEqual`; 404 when unset; checked before param validation; mounted before the maintenance gate), called by a daily Vercel Cron (Hobby limit) at 22:00 UTC. Same-origin deployment: `CLIENT_URL` = `SERVER_URL`, `TRUST_PROXY=1` (Vercel's edge is the one proxy), Secure cookies by default in production. → Tradeoffs: no live push over sockets (polling + web push instead); sweeps run daily instead of every 10 min / nightly; rate-limit counters (express-rate-limit memory store), the rider-location throttle and settings/category/template caches are per warm instance (looser limits, short cross-instance staleness) — acceptable until a shared store (Redis/Upstash) is added; uploads need Cloudinary and are capped by Vercel's 4.5 MB request body; 60 s max per request/cron run; chat auto-reply always sees staff as offline. Local `npm run dev` is unchanged (sockets + timers). How-to: `docs/deploy-vercel.md`.

**D-078 — MongoDB transactions for every financial write** · Billing moves money between ledgers (commission, seller balance, invoices, payouts) and must never double-charge or overdraw. → Dev (`config/db.ts`) and tests (`test/globalSetup.ts`) now run a single-node `MongoMemoryReplSet` (`storageEngine: 'wiredTiger'`) so multi-document transactions work everywhere (Atlas supports them). `lib/tx.ts` `withTx(fn)` wraps `session.withTransaction` (snapshot read, majority write; retried on transient errors, so `fn` has no outside side effects — audit/notify run after commit). Every store-scoped money transaction first bumps `Subscription.lockVersion` (`lockStoreFinance`), so two concurrent transactions of the same store conflict and one retries after seeing the other's writes (pay-from-balance, payout requests, invoice issuance, settlements, admin adjustments). Unique indexes back every idempotency claim (one charge per order, one renewal per period, one open upgrade, one pending payment per invoice, gateway transaction id, manual reference, payment idempotency key).

**D-079 — Flat 15% commission; the commission-rules engine is retired** · Owner rule: 15% on every successful sale regardless of plan. → `PLATFORM_COMMISSION_BPS = 1500` + `commissionSplit(base, shipping)` in `@souqly/shared` are the only source. Checkout snapshots it; the old `planCommissionBps` / `commissionDiscountBps` are removed. `CommissionRule` documents are kept (history) but never applied (`resolveCommissionBps` is unused); `POST/PATCH/DELETE /admin/commission-rules*` and `PUT /admin/stores/:id/commission` answer 409 `COMMISSION_FIXED`; `GET /admin/commission-rules` adds `meta: { locked: true, commissionBps }`; the admin store detail shows `commissionOverrideBps: null` + `legacyCommissionOverrideBps`.

**D-080 — Commission recognition and reversal** · → Base = product subtotal − seller-funded discounts (store promo/bundles/BXGY + store voucher); **shipping excluded**; platform vouchers/coins don't reduce it. `commission = round(base × 15%)` (half-up, paisa). Recognized only on **delivery** (`recognizeCommission`, from the delivered hook and re-derived by every billing/finance read and the sweep): one `CommissionEntry` charge per sub-order (partial unique index on `orderId`), and the order's `commission`/`sellerNet` snapshot is rewritten to the recognized values in the same transaction. Cancelled orders never get one. POS sales are not marketplace sales → no commission (unchanged from D-075; owner may revisit). Reversals only for **seller-borne refunds** (return refunds incl. dispute refunds, ref `return:<returnId>`) and a forced cancel after delivery (`cancel:<orderId>`): full return of every unit → the remaining commission exactly; partial → `floor(charge × returnedItemsValue / subtotal)`; cumulative reversals are capped at the charge (never negative). Admin goodwill refunds (`POST /admin/orders/:id/refund`) are platform-funded (the seller ledger isn't debited either) → no reversal (**owner to confirm**). Reversal status: COD charge still unbilled → `unpaid` (offsets it on the next invoice); already invoiced/paid → `credited` + seller ledger `commission_credit`; online → `deducted` (money handled by the ledger refund).

**D-081 — Subscriptions and the monthly billing cycle** · → One `Subscription` per store (created at onboarding or first billing touch; existing paid stores are grandfathered for their first period). Monthly periods keep an `anchorDay` (Jan 31 → Feb 28/29 → Mar 31). Every store, Free included, has periods because COD commission is billed monthly. The daily sweep (`billing.daily`) renews each ended period in one transaction: applies a scheduled downgrade/cancel, issues a `renewal` invoice for the NEXT period = fee of the plan active next period + one commission line with every `unpaid` COD entry recognized up to the cut-off (entries move `unpaid → invoiced` with a conditional update; the invoice is unique per `(storeId, periodStart)`) + `balance_recovery` when the seller balance is negative, then advances the period (catch-up loop ≤ 24 periods). No invoice when the total is 0 (Free with no dues). `dueDate = cut-off + graceDays` (Setting `billing.graceDays`, default 7, admin-editable). Unpaid reversals whose charge was billed earlier are credited to the balance at issuance.

**D-082 — Billing suspension is separate from moderation suspension** · → `Store.billingStatus: 'active' | 'suspended'` + `billingSuspension { reason: 'overdue' | 'admin', invoiceId, note, at, by }`; `Store.status` (moderation) is never touched, so `storeContext` still lets the seller into the Seller Center (billing, orders, finance, fulfilment). While billing-suspended: excluded from the public store index / store pages / store search / share image (`status: 'approved', billingStatus: { $ne: 'suspended' }`), `isStoreOpen` is false (cart lines `unavailable`, add-to-cart 400 `STORE_UNAVAILABLE`, checkout 409 `CART_CHANGED`), publishing returns 403 `BILLING_SUSPENDED`. Existing orders continue. A renewal invoice past due → `overdue` → suspension `reason: 'overdue'`; settling the last overdue renewal invoice lifts it automatically; an admin billing suspension (`reason: 'admin'`) is lifted only by an admin. Upgrade invoices never suspend (past due → `void`, the plan simply doesn't change). Free sellers are never suspended for a subscription fee (there is none) — only for unpaid commission dues past the deadline.

**D-083 — COD vs online money flow** · → COD: the seller already holds the cash, so delivered COD orders are **no longer seller balance credits** (they were in D-074); the commission is a receivable billed monthly. COD refunds that Souqly pays the buyer (wallet) are debited from the seller ledger in full (`min(total, refund)`), the commission part comes back as a reversal, and a resulting negative balance is moved onto the next renewal invoice (`balance_recovery` line + ledger `balance_transfer` credit). Online (gateway, still hidden until keys exist): delivery credits `sellerNet` (85% of base + shipping) available after `financeHoldDays`; online refunds keep the D-074 pro-rata debit. One-time migration (`migration.billingV1` setting): delete pre-billing `sale:` ledger rows of COD orders (pre-launch data only). New ledger types: `invoice_payment`, `commission_credit`, `balance_transfer`. Payout requests are now transactional (D-078).

**D-084 — Paying invoices** · → (a) **Balance**: atomic transfer from the available balance for the full amount due (ledger `invoice_payment:<paymentId>`), optional `idempotencyKey`. (b) **Manual** bank/JazzCash/EasyPaisa transfer: reference (unique while pending/approved via `refLock`) + optional proof (Souqly temp upload) → `pending` → admin approve (optionally a smaller verified amount = partial) / reject. (c) **Gateway**: Stripe Checkout over REST (no SDK) only when both `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` exist; otherwise 503 `PAYMENT_NOT_CONFIGURED` with `requiredEnv`. JazzCash/EasyPaisa invoice checkout is not built (503 with their env names). The invoice is settled only by `POST /api/v1/webhooks/stripe` (raw body, HMAC-SHA256 `Stripe-Signature`, 5-min tolerance, mounted before the JSON parser): amount + currency must match exactly (else `failed` + audit), the transaction id is unique, replays are no-ops, money arriving for an already-settled invoice is flagged for an admin refund. Sellers never make partial payments; admins can approve partial manual amounts. On full settlement: invoice `paid` (or `waived`), linked commission entries `paid`/`waived`, upgrade applied, overdue suspension lifted.

**D-085 — Plan changes** · → Upgrade (free→pro/premium, pro→premium) creates an `upgrade` invoice and takes effect **when paid**: the plan changes and a fresh monthly period starts at payment time. Amount = new plan price − prorated credit for the unused part of the current period, only if that period was paid or grandfathered (`floor(fee × remaining / period)`). A new upgrade voids the open one; due in `graceDays`, then voided. Downgrade/cancel are scheduled for `currentPeriodEnd`; `DELETE /seller/billing/scheduled-change` undoes them (and voids an open upgrade). Outstanding invoices/commission are always carried. Onboarding accepts `plan`: the store starts on Free and a paid choice gets an upgrade invoice immediately (works while the store is still pending review).

**D-086 — Plan limits** · → `PLANS` (shared): Free Rs 0 / Pro Rs 500 / Premium Rs 1,000 per month. Products 50 / 1,000 / unlimited (created, non-deleted; publishing also checks live = published + in review), staff 2 / 10 / 50, store sections 4 / 12 / 20, layouts classic-only / all / all, analytics 7d+30d / +90d, export, POS, bulk CSV, store flash deals, bundles+BXGY, featured products: Pro+; priority support: Premium only; vouchers on every plan; `customDomain` dropped (not built). Downgrades never delete or unpublish: over-limit items stay, new creations/publishes and gated create/edit calls get 403 `PLAN_LIMIT` (`details.requiredPlan`); listing/deleting marketing items and clearing featured products stay allowed.

**D-087 — Admin billing** · → New permissions `admin.billing.view|manage` in the single shared list: FINANCE and SUPER_ADMIN get both, ADMIN view only. `/admin/billing/*` uses per-route `can()` (no impersonation). Every admin money action is a `BillingAdjustment` record (`waiver`, `extension`, `plan_change`, `manual_payment`, `suspension`, `reactivation`) with a mandatory reason, plus an audit entry; nothing is silently edited or deleted. Seller side reuses `store.finance.view` (summary/invoices) and `store.finance.manage` (change plan, pay; OWNER by default). CSV exports use the injection-safe `streamCsv`. Platform bank/wallet accounts for manual transfers live in the `billing` setting (`manualAccounts`).

**D-088 — `business` plan renamed `premium`** · → `STORE_PLANS = ['free','pro','premium']`. `migrateBilling()` (on boot, on every billing sweep — so Vercel too — idempotent) rewrites `business` → `premium` on stores, subscriptions and plan requests through the raw collections; `normalizePlan()` maps any leftover `business` on reads. Legacy `POST /seller/plan/request` + `/admin/plan-requests` stay as a "comp request" path and `PATCH /admin/stores/:id/plan` remains; both now go through `adminSetPlan` (subscription + store + `plan_change` adjustment, no invoice).

**D-089 — Billing scheduling** · → `billing.daily` is registered in the cron sweep registry (`services/jobs/sweeps.ts`; Vercel Cron → `/internal/cron/all`) and runs in-process every 6 h + 20 s after boot locally. The global commission safety net only scans orders/returns touched in the last 45 days (hooks do the real work; per-store reads are unbounded). `POST /admin/billing/sweep` runs it on demand.

**D-090 — Billing follow-ups for the frontend** · → Response DTOs live in `shared/src/types/billing.ts` (server builders are typed against them). `GET /seller/billing/summary` and `/payment-options` are cheap reads (`balanceSnapshot`, no reconcile per request); the commission/ledger safety-net sync runs at most once per 10 min per store per instance, while delivery/refund/cancel hooks write commission and now also reconcile the seller ledger (refund debits), and an admin payout rejection writes its reversal credit immediately. `SellerStore` carries `billingStatus` + `billingSuspension { reason, at }` so every member sees the hold. Admin commission rows and adjustments carry `storeName`/`storeSlug`; `GET /admin/billing/invoices/:id/pdf` (billing.view, audited). Category `commissionBps` in admin category create/update is accepted but ignored (flat rate, D-079) rather than rejected, so older admin forms keep working.
