# Decisions Log

Format: **D-number — title** · context → decision → consequences.

**D-001 — Monorepo with npm workspaces** · Need shared types between client and server without publishing packages. → `shared/` is consumed as TypeScript source (`main: src/index.ts`). Vite compiles it for the client; `tsx` runs it in dev and `tsup` bundles it into the server build. → No build step for shared; one `npm install` at root.

**D-002 — Separate local git repo** · The user's home folder is already a git repo containing this project. → `souqly/` has its own `git init`. → Commits never touch the parent repo. Nothing is pushed.

**D-003 — Money in integer minor units, rates in basis points** · Floating point errors in prices, commission and voucher math. → All amounts stored as integers (paisa). Percentages as bps (1250 = 12.5%). → Display via `formatMoney()`.

**D-004 — JWT in httpOnly cookies with server-side sessions** · Need "log out all devices", sessions list and refresh-token theft detection. → Short access JWT (15 min) + opaque refresh token stored hashed in `Session` collection, rotated on each refresh; reuse of an old refresh token revokes all of the user's sessions. → Sessions page and admin "force logout" are simple DB updates.

**D-005 — Tenant isolation via StoreMember + storeContext middleware** · Multi-vendor data must never leak across stores. → Membership table `StoreMember {storeId, userId, role, customRoleId, permissions}`; seller routes get `req.store` only from membership. `x-store-id` header selects among the user's own stores. → One user may belong to several stores (owner of one, staff in another).

**D-006 — Dev fallbacks behind interfaces** · Must run with zero API keys. → `StorageService`, `EmailService`, `NotificationProvider`, `PaymentProvider`, `JobQueue`, each with a factory choosing the real implementation if env keys exist. In-memory MongoDB in development when `MONGODB_URI` is missing, auto-seeded on boot so the site is immediately usable. → Switching to real services is only an `.env` change.

**D-007 — Brand "Souq Dusk" design system** · Needs to feel premium, warm and trustworthy and distinct from Daraz (orange) and Amazon. → Deep teal primary + saffron accent + pomegranate for sales on a parchment background; lantern-arch motif in the logo. Plus Jakarta Sans / Readex Pro / Noto Nastaliq Urdu. → See CLAUDE.md "Design system".

**D-008 — Search without external engine** · No Algolia/Elastic keys. → MongoDB text index + a lightweight fuzzy layer (normalized trigram-ish regex on name/brand/tags, and Levenshtein-based "did you mean" against a vocabulary of product names, categories and stores). → Can swap to Atlas Search later behind `SearchService`.

**D-009 — Order split** · One checkout must create one order per store. → `Checkout` (parent, payment) → `Order` per store (sub-order, own status/timeline/shipping). Stock is decremented atomically with `findOneAndUpdate({stock: {$gte: qty}})` per variant; on any failure the already-decremented items are restored. → Works without replica-set transactions (memory server is standalone).

**D-010 — Images for demo data** · No copyrighted images allowed. → Seed generates original SVG placeholder product art (category-themed gradients + iconography + product name) stored via StorageService. → Fully offline, no licensing risk.

**D-011 — Refresh rotation: one Session doc per rotation** · Need reuse detection without false alarms from two tabs refreshing at once. → Refresh token = `<sessionId>.<random>`, only sha256 stored. Each refresh atomically revokes the old Session (`replacedBy` = new id) and creates a new one (keeps the original `createdAt`). Presenting a rotated token more than 15 s after rotation revokes ALL the user's sessions + audit `auth.refresh_token_reuse`; inside 15 s it returns 401 `SESSION_ROTATED` without clearing cookies. Rotated docs are TTL-deleted after 7 days (reuse detection window). An access token whose session was rotated returns `TOKEN_EXPIRED` so the client simply refreshes. → Sessions list only shows non-revoked docs.

**D-012 — Jobs are in-process only for now** · Redis/BullMQ are not installed. → `JobQueue` interface (`register`, `schedule`, `every`, `stop`) with an in-process setTimeout/setInterval implementation; no persisted Job collection. Scheduled jobs are lost on restart, so handlers must be idempotent and periodic sweeps must re-derive pending work from the DB. → A Redis implementation can be added behind the same interface when `REDIS_URL` is set.

**D-013 — Server test setup** · Fast, isolated, key-free tests. → vitest globalSetup starts ONE mongodb-memory-server; each test file uses its own random database. `NODE_ENV=test` never reads `server/.env` (so real SMTP/Twilio keys are never used by tests), rate limiters are skipped (`TEST_RATE_LIMIT=1` re-enables), bcrypt cost is 4 in tests (12 otherwise). Emails/SMS are captured in `consoleOutbox` / `notifyOutbox` from the console fallbacks.

**D-014 — Account schemas and API types live in @souqly/shared** · Client forms and server validation must agree. → Added `shared/src/schemas/account.ts` (profile, preferences, 2FA, mode, sessions, delete, verify-email) and `shared/src/types/api.ts` (`MeUser`, `Address`, `SessionInfo`, `PublicConfig`, `ApiError`).

**D-015 — Phone OTP details** · → Phones normalized to `+E.164`. If the account has 2FA, `/auth/otp/verify` also requires `totp` (401 `TOTP_REQUIRED`; the OTP stays valid for the retry). In production without Twilio, `/auth/otp/request` returns 503 `SMS_UNAVAILABLE` instead of pretending to send.

**D-016 — Change email is immediate + re-verify** · Per docs/api-auth.md. → Email is updated at once with `emailVerified=false` and a verification link goes to the new address (password required; audited with old/new address). No confirmation is sent to the old address yet (possible hardening later).

**D-017 — Local uploads are served inert** · Seed art is SVG (D-010) and users upload images. → `/uploads` responses carry `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` and `Cross-Origin-Resource-Policy: cross-origin`; avatar uploads are checked by magic bytes (jpg/png/webp, ≤ 2 MB).

**D-030 — Token-driven theming with inverted dark scales** · Need one class vocabulary that works in light and dark. → All colors are CSS variables holding "r g b" channels (`client/src/styles/tokens.css`) mapped in Tailwind with `<alpha-value>`. Under `.dark` the 50..950 scales are inverted, so tinted pairs like `bg-primary-50 text-primary-700` stay readable; solid brand fills use semantic tokens (`bg-primary text-primary-fg`, dark mode = light teal with dark text for AA contrast). → Components rarely need `dark:` variants. A subtree can be forced dark by adding the `dark` class (used for the auth panel and hero banners).

**D-031 — Logo: souq arch + saffron "S" + lantern dot** · Brand mark must be original and readable at 16px. → A pointed souq-doorway arch in deep teal carrying a saffron "S" ribbon with a lantern dot at the apex (it also reads as a price tag). Lockup = mark + "Souqly" (Plus Jakarta 800, "ly" in teal) + "سوقلي" (Readex Pro, saffron). The React `Logo` uses token colors (`--logo-arch`); PNG icons, maskable icon and OG image are generated from SVG by `client/scripts/generate-brand-assets.mjs` (headless Chromium).

**D-032 — Fonts per language** · Nastaliq is tall and its Latin glyphs are serif. → `html[lang=ur]` uses the stack Plus Jakarta Sans → Noto Nastaliq Urdu with line-height ~2 (Latin names, emails and numbers keep the brand face); `html[lang=ar]` uses Readex Pro. Codes, prices and OTP boxes are forced LTR (`dir="ltr"`, `.latin`).

**D-033 — Theme/language before first paint** · Avoid a flash of the wrong theme or direction. → The zustand UI store persists as `souqly-ui`; an inline script in `index.html` reads it and sets `<html class="dark" lang dir>` before React loads. i18next detects language from the html tag. When a user signs in, their saved preferences are adopted once; switcher changes are saved to `PATCH /account/preferences` when signed in.

**D-034 — Shared Zod schemas, translated client-side** · Schemas in `@souqly/shared` carry English messages. → The client installs a global Zod error map (built-in issues translated) and maps the schemas' custom English messages to `validation.*` keys (`client/src/lib/validation.ts`). → No duplicated schemas; all form errors are localized.

**D-035 — Unbuilt areas are hidden, not broken** · Seller/Admin navs and marketplace tabs reference later phases. → Dashboard nav items carry `ready: boolean` and only ready items render. Marketplace links (categories, search, cart, wishlist, chat) go to a real "coming in this release" page; the seller-onboarding CTA is behind `WIZARD_READY = false` and an honest notice. → No dead buttons; flipping a flag reveals a feature.

**D-036 — Guards and auth UX** · `RequireAuth` / `RequirePlatformStaff` / `RequireSellerMode` wait for `/auth/me` (no retries) and show a retryable error if the API is unreachable; `RequireGuest` never blocks rendering (login works even while the session check fails). `next` redirects accept only same-origin relative paths. Refresh-on-`TOKEN_EXPIRED` is single-flight in the axios interceptor.

**D-037 — Visual QA with a fixture-backed API mock** · The UI must be reviewable while the server is down or busy. → `e2e/screenshots.mjs` (BASE_URL env or `--base`) takes desktop 1440×900 and mobile 390×844 shots in light/dark per language, records `pageerror`/`console.error`, and `--mock` serves fixture `/api/v1` responses (signed-in user, addresses, sessions; `--admin` for a staff user).

**D-018 — Catalog visibility via an approved-store index** · Public products must belong to `approved` stores, but Product has no store status. → `getPublicStoreIndex()` (30 s in-process cache) lists approved stores (slug, name, isMall, city, holiday). Every public query adds `status: 'published'`, `deletedAt` absent and `storeId ∈ approved`. Holiday-mode stores stay visible; their cards carry `unavailable: true` and the detail page has `holidayMessage`. Store-level filters (`store`, `mall`, `city`) narrow that id list. → No denormalized store flags on products; caches are disabled under NODE_ENV=test.

**D-019 — Listing engine = one aggregation, cursor per sort** · Need 7 sorts with cursor pagination, including relevance. → `/products` runs `$match → ($addFields _rel) → cursor $match → $sort {field, _id} → $limit+1`. Relevance = `textScore + 0.15·ln(sold+1) + 0.1·rating` (popularity only when there is no text match). The existing `{v, id}` cursor encodes the sort value (works for the computed `_rel` too). `total` only on the first page; `facets=1` adds a `$facet` (brands, price range, rating buckets, colours, sizes from `variants.options`). `relevance` without `q` behaves like a popularity sort.

**D-020 — Search cascade details (D-008)** · → `$text` first (english stemming); if no hit, AND of per-token fuzzy regexes on `searchText` (`s.?h.?r.?t`); if still none, Levenshtein (≤1 for tokens ≤4 chars, else ≤2) against a vocabulary (category/brand/store names + published title tokens and tags, weighted, rebuilt lazily every 10 min) and results for the corrected query with `meta.didYouMean`. `/search/suggest` also returns `didYouMean` when the exact text search missed but fuzzy matched. Searches are logged to `SearchLog` (first page only); `DELETE /search/history` detaches the user id rather than deleting rows, so trending counts stay.

**D-021 — Product card/derived fields** · → `recomputeDerived()` (pre-save, and called explicitly before `insertMany`) sets `priceMin/priceMax/compareAtMax/discountPct/totalStock` plus an extra `compareAtMin` (compare-at of the cheapest variant) so a card can show "was/now" without loading variants. `totalStock` counts active variants, stock − reserved. `stockLeft` is sent only when `< 10`.

**D-022 — Seller products** · → `/seller/products*` behind `requireAuth + storeContext + requirePermission(store.products.view|manage)`. Every lookup is `{_id, storeId: req.store._id}` (foreign ids → 404). Schemas are `.strict()`, so `storeId`/`status`/counters in the body are rejected (400). Descriptions/size guides go through `sanitizeRichText`; other strings through `stripHtml`. Media URLs must be `/uploads/...` or `https://res.cloudinary.com/...`. Editing keeps variant ids/`reserved` when `id` is sent. DELETE is a soft delete (`deletedAt` + `archived`). Publish → `published` for approved Mall stores or when the `autoApproveProducts` setting is true, otherwise `pending_review`.

**D-023 — Seller uploads** · → `POST /seller/uploads` (multipart `file`, multer limit 30 MB) sniffs magic bytes: jpg/png/webp/avif images ≤ 5 MB, mp4/webm videos ≤ 30 MB; stored under `stores/<storeId>/images|videos`. Uploads are audited.

**D-024 — Seed art at fixed keys** · Re-seeding the in-memory dev DB on every boot would pile up files. → `UploadOptions.fixedKey` (seed only) writes art to deterministic paths under `seed/` (products, stores, home, campaigns), so a re-seed overwrites identical files. `seed:clear` wipes the `seed/` folder (local) or deletes the seed keys (Cloudinary). Seed content is deterministic (mulberry32 PRNG seeded per store/product), so `runSeed({reset})` reproduces the same slugs, prices and counts. Demo password is bcrypt-hashed once per run and reused for every demo user.

**D-025 — Public store DTO is an allow-list** · → `toStorePublic` builds the response from named fields only; `business`/`payout` are also `select: false`. Never exposed: `ownerId`, contact email/phone (only `contact.whatsapp`), `business`, `payout`, `healthScore`, `plan`. The `store` query param on `/stores/:slug/products` is ignored (scope is forced to that store).
